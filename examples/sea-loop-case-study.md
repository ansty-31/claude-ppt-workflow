# SEA-Loop 中期答辩 PPT 制作案例研究

## 项目背景

**需求**：为海洋自主观测浮标系统（SEA-Loop）制作中期答辩 PPT  
**目标受众**：高校教师评审团  
**页数**：16 页主讲 + 6 页备答  

**实际投入**：
- **成本：≥$50**（最后一天尝试投影版改造约 $30，前期制作约 $20+）

**结果**：可编辑版交付成功；投影版（字号放大+光晕）因技术问题未完成。

---

## 制作过程

### 第一阶段：可编辑版 PPTX 生成（成功）

**方案**：全程 python-pptx 代码生成

**遇到的问题**：
1. 中文字体需要手动设置 `a:ea` 属性
2. 图表刻度标签在 LibreOffice 导出 PDF 时偏移
3. 光晕效果在预览 PDF 中不可见

**验收**：
- 22 页生成成功，6 页隐藏
- 字体检查通过（Noto Sans CJK SC）
- 数据图表与实验记录一致

**产出**：完整的可编辑 PPTX

---

### 第二阶段：投影版尝试（失败）

#### 技术方案

1. `theme.py` 增加 `G2` 开关，控制字号和光晕
2. 用 3 个子代理并行改造不同页面
3. 主调度统一验收

#### 实际执行

**派发子代理并行改造**：
- **slides_hw + charts**：读了 1.3MB SVG → 上下文爆炸，崩溃
- **slides_algo**：同样读 SVG 崩溃，重派新代理接手
- **slides_end**：完成改造，但达到 30 轮限制，人工接手修孤字

**最终状态**：
- 完成：p14–16（slides_end.py）
- 未完成：p1–13 部分页面

**实际成本**：约 $30（最后一天）

---

## 失败原因分析

### 1. 技术债：读大文件导致上下文爆炸

**现象**：
```bash
Read(file_path="第08页_完整改进_字体层级加G2.svg")  # 1.3MB
→ autocompact thrashing after 3 turns
```

**根因**：设计稿是 SVG 格式，包含完整的字体嵌入和路径数据。

**应对**：
```bash
# 正确做法：预提取坐标（5 分钟人工）
python3 extract_coords.py teacher_08.svg > teacher_08.txt  # 4KB
```

**教训**：永远不要让 Claude 读 >200KB 的单个文件。

---

### 2. 任务拆解：子代理职责不清

**错误 Prompt**：
```
先审一遍这些 G2 分支，再补齐剩下的部分
```

**后果**：
- 子代理花 5–10 轮反复 Read 已改代码
- 达到 30 轮限制时仍未完成主要工作

**正确 Prompt**：
```
只改 slides_hw.py 的 pool() 函数：
- GIF 宽度改为 8.0 英寸
- 步骤字号 22/18
- WARN 文本两行，宽度 3.35 英寸
不要读其他函数，不要审查已有 G2 分支。
```

**教训**：给子代理的任务必须是"单个函数 + 明确的数值改动"，不要"审查后决定"。

---

### 3. 验证策略：增量验证 vs 全量验证

**错误做法**：
```python
# 子代理只构建单页验证
prs = new_deck()
slides_end.progress(prs)
prs.save("/tmp/g2/end/deck.pptx")  # 只有 1 页
```

**后果**：
- lines.py 报的页码错误（p14 实际是 p1）
- 隐藏页数统计错误

**正确做法**：
```python
# 始终构建完整 22 页 deck
for f in build.main_slides():
    f(prs)
build.slides_end.backups(prs)
build.keep_left_margin(prs)
# 然后只检查目标页：lines.py deck.pdf 14 15 16
```

**教训**：验证环境必须与最终环境一致。

---

### 4. 并行协作：文件依赖冲突

**场景**：
- slides_hw.py 和 slides_algo.py 都调用 `charts.depth_chart()`
- 两个子代理并行修改 charts.py → 潜在竞态

**应对**：
1. 明确"不要改 theme.py / charts.py，如需改动停下并报告"
2. 主调度负责改共享模块
3. 子代理各自输出到独立验证目录

**教训**：并行任务必须在文件级隔离，或由主调度串行处理共享依赖。

---

## 如果重来，应该怎么做？

### 方案 A：用生图模型

**步骤**：
1. 可编辑版 PPTX 导出 16 页 PDF
2. 每页截图 → 调用生图模型："放大字号到 34–36pt，保持布局和配色"
3. 生成 16 张 PNG，合并为 PDF

**优势**：
- 字体渲染完美（不受 PowerPoint/LibreOffice 差异影响）
- 光晕效果可控
- 无需处理 python-pptx 的字体映射

**劣势**：
- 不可编辑（后续修改需要重新生图）

---

### 方案 B：可编辑版（优化流程）

**步骤**：
1. **预处理**（5 分钟人工）：
   ```bash
   python3 extract_coords.py teacher_*.svg > teacher_*.txt
   ```

2. **串行改造**（不用子代理）：
   ```bash
   # 主调度自己改，避免并行协调成本
   改 theme.py G2 基础设施 → 改 slides_intro.py (p1-3) → 
   改 slides_hw.py (p4-7) → 改 charts.py + slides_hw.py (p8) → ...
   ```

3. **增量验证**：
   ```bash
   # 每改 3–4 页，跑一次 lines.py
   python3 build_g2.py && python3 lines.py output/deck.pdf 1 2 3 4
   ```

**耗时**：2–3 小时（vs 实际 >8 小时）

---

### 方案 C：混合方案（推荐）

**步骤**：
1. 可编辑版 PPTX 保持可编辑（用于数据更新）
2. 投影版用生图模型生成（用于实际答辩）
3. 如需修改：改可编辑版 PPTX → 重新生图

**优势**：
- 兼顾可编辑性和视觉质量

---

## 核心教训

### 1. 成本不等于直接开销

**本次实际成本分解**：
- 有效工作（可编辑版 PPTX）：少部分
- 投影版基础设施（可复用）：少部分
- 子代理崩溃浪费：数美元
- 返工修孤字：少部分
- 未完成部分（沉没成本）：少部分
- 前期试错（探索 python-pptx）：主要部分

**教训**：试错成本远高于实际生成成本。第一次尝试新方案时，预算应 ×3。

---

### 2. 人工预处理 > 让 AI 自动化一切

**案例**：提取 SVG 坐标

```bash
# AI 自动化方案（失败）
让子代理"读 SVG 并提取关键坐标" 
→ 1.3MB 文件进上下文 → 崩溃

# 人工预处理（成功）
python3 extract_coords.py input.svg > output.txt  # 5 分钟
→ 4KB 文本文件，子代理正常工作
```

**教训**：5 分钟人工可以省数美元和数小时返工时间。

---

### 3. 明确"可编辑"的真实需求

**用户最初需求**："可编辑的投影版 PPTX"

**实际场景分析**：
- 答辩前会再改数据吗？**否**（数据已定稿）
- 需要在不同设备上演示吗？**是**（教室投影仪 + 备用笔记本）
- 答辩后需要分发给评委吗？**是**（PDF 格式）

**结论**：真实需求是"高质量的 PDF"，而非"可编辑的 PPTX"。生图方案更合适。

**教训**：澄清需求背后的使用场景，避免过度工程。

---

### 4. 子代理不是银弹

**适用场景**：
- 独立的审查任务（bugs / perf / security 并行分析）
- 数据驱动的批量生成（100 个相似页面，各自独立）

**不适用场景**：
- 有共享依赖的代码改造（theme.py 被所有 slides_*.py 依赖）
- 需要"审查后决定"的任务（无法预先明确改动点）

**教训**：有共享依赖 + 需要迭代调整 → 主调度自己串行做，不要并行派发。

---

## 保留成果

尽管投影版失败，但以下产出可复用：

### 1. 工具脚本
- `lines.py`：孤字/越界/重叠检查（通用，可用于任何 PPT）
- `extract_coords.py`：从 SVG 提取坐标（避免读大文件）
- `bfull.py`：完整 deck 构建模板

### 2. 经验文档
- 坑点与省钱指南
- 本案例研究

### 3. 代码模块
- `theme.lines()`：平衡断行函数（解决孤字问题）
- `theme.at()`：基线坐标换算（精确定位文本）
- G2 分支代码（虽未完成，但可作为未来参考）

**估值**：如果下次遇到类似需求，这些积累可省下大量成本。

---

## 给后来者的建议

如果你要用 AI 制作 PPT：

1. **第一次尝试新方案**：预算 ×3，时间 ×2
2. **大文件必须预处理**：>200KB 的 SVG / PDF / 图片，先提取关键信息
3. **子代理只做明确任务**：不要"审查后决定"，要"改这 5 行代码"
4. **验证环境 = 生产环境**：不要在 1 页 deck 上验证，要在完整 deck 上验证
5. **澄清"可编辑"需求**：如果只是为了投影，生图方案可能更合适

**最重要的**：
```
成本 = 有效工作 + 试错浪费 + 返工成本
降低总成本的关键不是"少用 AI"，而是"减少试错和返工"
```

---

**结论**：失败也是宝贵的数据点。这 $50 的投入换来了可复用的工具、经验文档和"什么情况下不该用 AI"的清晰认知。

如果你要用 AI 制作 PPT：

1. **第一次尝试新方案**：预算 ×3，时间 ×2
2. **大文件必须预处理**：>200KB 的 SVG / PDF / 图片，先提取关键信息
3. **子代理只做明确任务**：不要"审查后决定"，要"改这 5 行代码"
4. **验证环境 = 生产环境**：不要在 1 页 deck 上验证，要在完整 deck 上验证
5. **澄清"可编辑"需求**：如果只是为了投影，生图方案可能更合适

**最重要的**：
```
成本 = 有效工作 + 试错浪费 + 返工成本
降低总成本的关键不是"少用 AI"，而是"减少试错和返工"
```
