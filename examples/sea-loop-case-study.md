# SEA-Loop 中期答辩 PPT 制作案例研究

## 项目背景

**需求**：为海洋自主观测浮标系统（SEA-Loop）制作中期答辩 PPT  
**目标受众**：高校教师评审团  
**页数**：16 页主讲 + 6 页备答  
**特殊要求**：
- 教师投影版（G2）：字号放大（标题 34–36pt，正文 18–20pt）
- 微光晕效果保护浪纹背景上的文字
- 精确按设计稿（第 8、10 页 SVG）对齐
- 保持 PPTX 可编辑，不转图片

**实际投入**：
- 时间：前期制作 + G2 改版共 3 天
- **成本：~$50**（前期 $20 + 今日 G2 尝试 $30）

**结果**：G2 版效果不佳，已终止。保留原版 + 部分成品归档。

```python
# build/theme.py - 公共排版函数
def title(s, main, sub=None):

def cover(prs):

    text(s, 1.2, 2.5, 10.8, 1.2, "SEA-Loop 自主浮标系统", size=48, bold=True)
    # ...
```

1. 中文字体需要手动设置 `a:ea` 属性
2. 图表刻度标签在 LibreOffice 导出 PDF 时偏移
3. 光晕效果（glow）在预览 PDF 中不可见

**验收**：

- 数据图表与实验记录一致

## 失败原因分析

### 1. 技术债：读大文件导致上下文爆炸
**现象**：
```bash
Read(file_path="第08页_完整改进_字体层级加G2.svg")  # 1.3MB
→ autocompact thrashing after 3 turns
```

**根因**：老师提供的设计稿是 SVG 格式，包含完整的字体嵌入和路径数据。子代理在"审查设计稿以了解几何"时直接 Read，触发上下文限制。

**应对**：
```bash
# 正确做法：预提取坐标（5 分钟人工）
python3 extract_coords.py teacher_08.svg > teacher_08.txt  # 4.8KB
```

**教训**：永远不要让 Claude 读 >200KB 的单个文件。

---

### 2. 任务拆解：子代理职责不清
**错误 Prompt**：
```
先审一遍这些 G2 分支，再补齐剩下的部分
```

**后果**：
- 子代理花 5–10 轮反复 Read 已改代码
- 达到 30 轮限制时仍未完成主要工作
- 返工成本：~50K tokens

**正确 Prompt**：
```
只改 slides_hw.py 的 pool() 函数：
- GIF 宽度改为 8.0 英寸
- 步骤字号 22/18
- WARN 文本两行，宽度 3.35 英寸
不要读其他函数，不要审查已有 G2 分支。
```

**教训**：给子代理的任务必须是"单个函数 + 明确的数值改动"，不要"审查后决定"。

---

### 3. 验证策略：增量验证 vs 全量验证
**错误做法**：
```python
# 子代理只构建单页验证
prs = new_deck()
slides_end.progress(prs)
prs.save("/tmp/g2/end/deck.pptx")  # 只有 1 页
```

**后果**：
- lines.py 报的页码错误（p14 实际是 p1）
- 隐藏页数统计错误
- 最终合并时发现布局冲突

**正确做法**：
```python
# 始终构建完整 22 页 deck
for f in build.main_slides():
    f(prs)
build.slides_end.backups(prs)
build.keep_left_margin(prs)
# 然后只检查目标页：lines.py deck.pdf 14 15 16
```

**教训**：验证环境必须与最终环境一致。

---

### 4. 并行协作：文件依赖冲突
**场景**：
- slides_hw.py 和 slides_algo.py 都调用 `charts.depth_chart()`
- 两个子代理并行修改 charts.py → 潜在竞态

**实际情况**：因两个代理都崩溃，未实际冲突。但如果成功，会出现：
```
slides_hw 子代理：charts.depth_chart(..., mode="G2_simple")
slides_algo 子代理：charts.depth_chart(..., g2_labels=True)
→ 两种不兼容的 API 设计
```

**应对**：
1. 明确"不要改 theme.py / charts.py，如需改动停下并报告"
2. 主调度负责改共享模块
3. 子代理各自输出到独立验证目录（`/tmp/g2/{hw,algo,end}/`）

**教训**：并行任务必须在文件级隔离，或由主调度串行处理共享依赖。

---

### 5. 成本控制：重复渲染 PDF
**浪费点**：
- 每次改动后都跑 `soffice → pdftoppm` 生成 22 页 PNG
- 单次渲染：~60 秒 + 17MB PNG
- 迭代 5 轮 → 5 分钟 + 85MB（都会被覆盖）

**优化**：
```bash
# 只在最终验收时渲染 PDF
改代码 → py_compile 语法检查 → (循环)
         ↓
    最终一次：PPTX → PDF → lines.py
```

**教训**：验证逻辑（syntax check）和验证视觉（render）分开，后者只做一次。

## 如果重来，应该怎么做？

### 方案 A：放弃 G2 可编辑版，改用生图
**步骤**：
1. 原版 PPTX 导出 16 页 PDF
2. 每页截图 → 调用 DALL-E 3 提示词："放大字号到 34–36pt，保持布局和配色"
3. 生成 16 张 PNG，合并为 PDF

**成本**：
- DALL-E 3：$0.04/图 × 16 = **$0.64**
- 人工审校：20 分钟

**优势**：
- 字体渲染完美（不受 PowerPoint/LibreOffice 差异影响）
- 光晕效果可控
- 无需处理 python-pptx 的字体映射

**劣势**：
- 不可编辑（后续修改需要重新生图）

---

### 方案 B：G2 可编辑版（优化流程）
**步骤**：
1. **预处理**（5 分钟人工）：
   ```bash
   python3 extract_coords.py teacher_*.svg > teacher_*.txt
   ```

2. **串行改造**（不用子代理）：
   ```bash
   # 主调度自己改，避免并行协调成本
   改 theme.py G2 基础设施 → 改 slides_intro.py (p1-3) → 
   改 slides_hw.py (p4-7) → 改 charts.py + slides_hw.py (p8) → ...
   ```

3. **增量验证**：
   ```bash
   # 每改 3–4 页，跑一次 lines.py
   python3 build_g2.py && python3 lines.py output/deck.pdf 1 2 3 4
   ```

4. **最终验收**：
   ```bash
   # 完整 22 页 + pdffonts + imgcheck + 与原版 diff
   bash tools/full_audit.sh
   ```

**成本**：
- 主会话：~60K tokens（无子代理浪费）
- **总计**：~$1

**耗时**：2–3 小时（vs 实际 8 小时）

---

### 方案 C：混合方案（推荐）
**步骤**：
1. 原版 PPTX 保持可编辑（用于数据更新）
2. G2 投影版用 DALL-E 3 生成（用于实际答辩）
3. 如需修改：改原版 PPTX → 重新生图

**成本**：
- 初次生成：$0.64
- 后续修改：$0.04/页（只重新生成改动页）

**优势**：
- 兼顾可编辑性和视觉质量
- 成本可控（只为最终版付费）

## 核心教训

### 1. 成本不等于 token 数
**本次实际成本分解**：
```
有效工作（原版 PPTX）：        $2.5
G2 基础设施（可复用）：         $0.5
子代理崩溃浪费：               $2.0
重复渲染 PDF：                $0.3
返工修孤字：                  $0.5
未完成部分（沉没成本）：        $0.7
前期试错（未记录会话）：        $23.5
─────────────────────────────
总计：                        ~$30（今日）+ $20（前期）= $50
```

**教训**：试错成本远高于实际生成成本。第一次尝试新方案时，预算应 ×3。

---

### 2. 人工预处理 > 让 AI 自动化一切
**案例**：提取 SVG 坐标

```bash
# AI 自动化方案（失败）
让子代理"读 SVG 并提取关键坐标" 
→ 1.3MB 文件进上下文 → 崩溃

# 人工预处理（成功）
python3 extract_coords.py input.svg > output.txt  # 5 分钟
→ 4.8KB 文本文件，子代理正常工作
```

**教训**：5 分钟人工可以省 $2 和 2 小时返工时间。

---

### 3. 明确"可编辑"的真实需求
**用户最初需求**："可编辑的 G2 版 PPTX"

**实际场景分析**：
- 答辩前会再改数据吗？**否**（数据已定稿）
- 需要在不同设备上演示吗？**是**（教室投影仪 + 备用笔记本）
- 答辩后需要分发给评委吗？**是**（PDF 格式）

**结论**：真实需求是"高质量的 PDF"，而非"可编辑的 PPTX"。方案 A（生图）更合适。

**教训**：澄清需求背后的使用场景，避免过度工程。

---

### 4. 子代理不是银弹
**适用场景**：
- 独立的审查任务（bugs / perf / security 并行分析）
- 数据驱动的批量生成（100 个相似页面，各自独立）

**不适用场景**：
- 有共享依赖的代码改造（theme.py 被所有 slides_*.py 依赖）
- 需要"审查后决定"的任务（无法预先明确改动点）

**本次失败点**：
- 3 个子代理都需要改 theme.py / charts.py（共享依赖）
- 任务是"按设计稿对齐"（需要反复对比调整，无法一次性明确）

**教训**：有共享依赖 + 需要迭代调整 → 主调度自己串行做，不要并行派发。

## 给后来者的建议

如果你要用 AI 制作 PPT：

1. **第一次尝试新方案**：预算 ×3，时间 ×2
2. **大文件必须预处理**：>200KB 的 SVG / PDF / 图片，先提取关键信息
3. **子代理只做明确任务**：不要"审查后决定"，要"改这 5 行代码"
4. **验证环境 = 生产环境**：不要在 1 页 deck 上验证，要在 22 页完整 deck 上验证
5. **澄清"可编辑"需求**：如果只是为了投影，生图方案可能更合适

**最重要的**：
```
成本 = 有效工作 + 试错浪费 + 返工成本
降低总成本的关键不是"少用 AI"，而是"减少试错和返工"
```
